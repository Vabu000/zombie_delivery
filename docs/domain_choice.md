# Обґрунтування вибору предметної області (ЛР №1)

## 1. Назва проекту
**Zombie Night Delivery Aggregator (Агрегатор нічної доставки в умовах постапокаліпсису)**

## 2. Актуальність та проблематика
У класичних міських логістичних системах (на зразок Glovo, Uber Eats, Bolt Food) ключовими метриками є швидкість та вартість доставки. Проте в умовах зомбі-апокаліпсису логістика стикається з кардинально новими викликами:
- **Нічний час найвищої активності**: безпечне пересування живих кур'єрів у нічні години стає неможливим через переповнені ордами вулиці.
- **Використання зомбі-кур'єрів**: одомашнені або керовані імплантами зомбі-кур'єри можуть безперешкодно рухатися зараженими зонами без ризику бути атакованими нежиттю.
- **Критична цінність вантажів**: клієнти (виживаючі у бункерах та сховищах) замовляють життєво необхідні ресурси: медикаменти, антидоти, кров/плазму, консерви та патрони, тоді як платою за доставку виступають раціони або біологічні зразки ("мізки" / "свіже м'ясо").
- **Динамічний рівень небезпеки**: маршрути проходять через зони різної інтенсивності зараження (`LOW`, `MEDIUM`, `HIGH`, `NIGHTMARE`), що вимагає динамічного розрахунку вартості та ризику.

## 3. Обґрунтування вибору
1. **Повна відповідність архітектурним патернам сучасних веб-додатків**:
   - Система агрегатора вимагає чіткого розмежування трьох незалежних ролей: **Клієнт** (замовник), **Кур'єр** (виконавець) та **Адміністратор/Overlord** (диспетчер та координатор системи).
   - Присутні сутності реального світу: Користувачі, Замовлення/Доставки, Географічні координати, Статуси життєвого циклу замовлення.
2. **Багатий простір для реалізації бізнес-логіки (MVP)**:
   - Автоматичний розрахунок винагороди кур'єра на основі типу вантажу та коефіцієнта небезпеки зони.
   - Складний життєвий цикл доставки: `PENDING` -> `IN_TRANSIT` -> `DELIVERED` / `CANCELLED`.
   - Заборона редагування маршруту після того, як кур'єр вирушив у рейс або виконав замовлення.
3. **Демонстрація інформаційної безпеки (RBAC та захист від IDOR)**:
   - **Вертикальний контроль доступу**: звичайний клієнт не може бачити внутрішню адмін-панель або брати замовлення в якості кур'єра.
   - **Горизонтальний контроль доступу (IDOR)**: клієнт має доступ виключно до власних замовлень і не може переглядати, змінювати чи скасовувати замовлення інших виживаючих або змінювати чужі облікові записи.
4. **Масштабованість для наступних лабораторних робіт курсу**:
   - Архітектура легко інтегрується з кешуванням (Redis) для швидкої видачі списків доступних замовлень, чергами задач (Celery / RabbitMQ) для фонового прорахунку маршрутів, геопросторовими індексами (PostGIS) та балансуванням навантаження (Nginx).

## 4. Сутності предметної області
| Сутність | Опис | Ключові атрибути |
| :--- | :--- | :--- |
| **User** | Обліковий запис користувача системи | `id`, `username`, `role` (user/courier/admin), `is_admin`, `full_name`, `created_at` |
| **Delivery** | Замовлення на доставку провізії/ресурсів | `id`, `title`, `target_lat`, `target_lon`, `prey_type`, `danger_level`, `status`, `reward_brains`, `owner_id`, `courier_id` |
| **Zone/Danger** | Рівень загрози зони доставки | `LOW` (1.0x), `MEDIUM` (1.5x), `HIGH` (2.0x), `NIGHTMARE` (3.0x) |
